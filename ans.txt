1. Executive Summary
=====================================================================================
AIMHRA (AI-based Maternal Health Risk Analysis and Decision-Support System) is a
full-stack clinical decision-support web application with:
- A Django/DRF REST backend (backend/) serving JWT-authenticated APIs for 9 Django
  apps: core, audit, accounts, patients, assessments, mlcore, kb, chat, reports.
- A React 19 + Vite SPA (frontend/) with role-based routing for two staff roles:
  HEALTHCARE_WORKER and ADMIN.
- An ML layer that trains Random Forest and XGBoost on Mathernal_Risk.csv (6,103 raw
  rows -> 6,057 after cleaning) over 8 features, serving the "production" model
  through a thread-safe registry, with SHAP TreeExplainer explanations per prediction.
- A deterministic, versioned rule engine (assessments/rules/rules.json, v1, 21 rules,
  4 categories) that outranks everything (ML, RAG, LLM) for emergencies.
- A RAG knowledge base (kb app): ingestion, chunking, TF-IDF/OpenAI embeddings,
  cosine retrieval over DocumentChunk vectors (or optional Qdrant).
- An LLM chat assistant (chat app) with a non-diagnosis system prompt, emergency
  keyword bypass, and graceful fallbacks.
- PDF report generation with ReportLab (reports app).
- Audit logging (audit app) for 19 action types with key redaction.

The working tree documents an in-progress role refactor: PATIENT was removed as an
application role (pages/patient/* and Register.jsx deleted; new 0002 migrations in
accounts, patients, audit). Patients are now standalone clinical records, not users.

=====================================================================================
2. What AIMHRA Does
=====================================================================================
Purpose: A healthcare worker logs in, maintains maternal patient records, enters
clinical measurements at each visit, and the system:
1. Runs an ML model classifying the patient "low risk" / "mid risk" / "high risk".
2. Explains the prediction with SHAP (per-feature contributions).
3. Runs independent clinical safety rules (e.g., systolic BP >= 160 -> EMERGENCY)
   and creates alerts.
4. Stores everything to show a longitudinal history and trend (improving/stable/increasing).
5. Can generate a PDF report for any assessment.
6. Provides a RAG-grounded AI assistant per patient that escalates emergency language
   deterministically.

Intended users (accounts/models.py): HEALTHCARE_WORKER and ADMIN only. Patients are
NOT users (patients/models.py docstring).

End-to-end flow (verified in code):
User Login -> POST /api/auth/login/ -> JWT -> Role Dashboard -> Patient list -> Patient
Detail workspace -> New Assessment -> client validation -> POST /api/assessments/ ->
AssessmentSerializer validation -> create_assessment() -> registry.predict -> SHAP ->
rules.evaluate -> transaction.atomic (Assessment+Prediction+Alert) -> audit -> trend ->
JSON response -> UI -> History/Trend -> PDF report -> AI assistant.

  +-- kb.services (RAG retrieval) -> chat.llm (OpenAI-compatible generation)

- Service: transactional workflows (create_assessment, generate_report, respond,
  index_document) - no HTTP knowledge.
- Selectors: reusable query/scope logic (patients/selectors.py).
- Registry: the only place that touches model artifacts.
- Frontend never calls axios directly from components; goes through api/client.js and
  services/auth.js.

9. Authentication and Authorization
=====================================================================================
Login flow (traceable):
1. Login.jsx -> authService.login -> POST /api/auth/login/ {username,password}.
2. LoginView (TokenObtainPairView) -> CustomTokenObtainPairSerializer.validate:
   - calls SimpleJWT to authenticate,
   - REJECTS any role outside {HCW, ADMIN} (legacy PATIENT) with AuthenticationFailed +
     LOGIN_FAILED audit (reason role_not_allowed),
   - any failure logs LOGIN_FAILED and re-raises,
   - on success logs LOGIN and embeds UserSerializer as data["user"].
3. Response {access, refresh, user}; frontend stores tokens in localStorage, sets user,
   navigates to /app/dashboard or location.state.from.
4. Every request carries Authorization: Bearer <access> (axios interceptor).
5. On 401: refresh once via /api/auth/refresh/ (CustomTokenRefreshSerializer re-checks
   role + is_active from DB before minting new access - closes legacy refresh loophole).
6. Logout: /api/auth/logout/ -> RefreshToken(refresh).blacklist(); frontend clears tokens.
7. Session restore: AuthContext calls GET /api/auth/profile/ if token exists; 401 clears.

Tokens/permissions: default IsAuthenticated; views layer IsHealthcareWorker / IsAdmin /
object checks. Object-level access centralized in patients/selectors.py:
- patient_ids_for_healthcare_worker = created UNION assigned.
- can_access_patient(user, profile): ADMIN all; HCW creator-or-assigned; else False.
- scoped_patient_queryset: queryset-level enforcement.
This helper is reused by assessments, alerts, reports, chat. ProtectedRoute.jsx is UX-only;
backend is authority (tests prove 403 + no data leak).

Role matrix (verified):
- Login both. Patients: worker own+assigned, admin all. Assessments/alerts/reports/chat for
  accessible patients both. Alert ack both (IsHealthcareWorker). KB upload/delete/reindex:
  admin only (403 worker). Model activate: admin. Audit list: admin. User mgmt: admin.
  System stats: admin.

Patient-role removal (already implemented):
- accounts/0002: role choices -> HCW/ADMIN + data migration deactivate_legacy_patient_accounts
  (is_active=False on PATIENT rows, never deleted).
- patients/0002: copies user's name/email/phone onto PatientProfile then REMOVES the user
  OneToOne FK; adds created_by etc.
- Login+refresh guards; tests cover legacy login/refresh/access rejection; protected route

11. Maternal Risk Assessment
=====================================================================================
The 8 model features (exactly mlcore/constants.FEATURES, order matters):
age (UI 14-55) | body_temperature (deg F, 95-106) | heart_rate bpm (40-200) |
systolic_bp mmHg (70-250, must >= diastolic) | diastolic_bp mmHg (40-150) |
bmi (12-60) | hba1c "HbA1c column (dataset units)" observed 30-50 (20-60) |
fasting_glucose "fasting column" observed 3.5-8.9 (2-20).

constants.py documents the glucose unit inconsistency and records it rather than
silently "fixing" it.

Also collected but NOT model inputs: visit_date (not future), gestational_week (1-45,
optional), symptoms (12-token vocabulary from rules.json), notes. Patient demographics
(name, DOB, blood group...) are recordkeeping only.

Serialization path: AssessmentSerializer (ModelSerializer) - read_only id/patient/
created_at/prediction; get_prediction embeds linked prediction; validators:
validate_visit_date (no future), validate_gestational_week, validate_symptoms
(tokens must be in rules.json vocabulary), cross-field validate() applies the
SAME PLAUSIBILITY_RANGES used to clean training data + diastolic <= systolic.

12. Machine Learning Pipeline
=====================================================================================
Files: constants -> dataset -> preprocessing -> training -> evaluation -> registry ->
explain; commands train_models/inspect_dataset; models.py (ModelVersion).

Dataset (backend/data/Mathernal_Risk.csv; duplicate at root; md5 6ad779f6...70dab)
= 6,103 rows x 11 cols, no missing values. Target Status -> risk_level:
low 2001 / mid 2043 / high 2059 (near-balanced 33/33/33 so resampling rejected).
COLUMN_MAP maps headers to canonical names. Excluded: Patient ID, Name (identifier + PII);
LEAKAGE_FEATURES = [] with a documented review (all features are point-of-assessment).

Cleaning (clean_dataset): drop exact duplicates on features+label (1 row) + implausible
rows outside PLAUSIBILITY_RANGES (45 rows) -> 6,057 rows. Every drop counted; persisted by
inspect_dataset into backend/data/dataset_report.json.

Split & preprocessing: stratified 70/15/15, random_state=42. Preprocessor =
median imputation only, fitted on training split, serialized into the joblib bundle as a
dict (to_dict/from_dict). No scaling (trees need none).

Models (training.py):
RF: n_estimators=400, min_samples_leaf=2, class_weight="balanced_subsample", random_state=42.
XGB: n_estimators=400, learning_rate=0.08, max_depth=6, subsample=0.9,
colsample_bytree=0.8, tree_method="hist", eval_metric="mlogloss", random_state=42.
Labels encoded to indices of RISK_LEVELS (probability columns align for both models).
quick=True trains 10-tree models for tests only (never production).
Bundle per model: {model_name, model, preprocessor, features, classes, dataset_md5,
trained_at, train_config} -> ml_artifacts/{randomforest,xgboost}_{full,quick}.joblib.

Evaluation (evaluation.py): accuracy, macro precision/recall/F1, high_risk_recall
("a missed high-risk case is the costliest error"), per-class metrics, confusion matrix,
ROC-AUC OVR macro. selection_score: default high_risk_recall_then_f1 (tuple high-risk
recall, macro F1, AUC); macro_f1 / accuracy alternatives. "Accuracy is never the sole basis."

Registration (train_models command): winner by criterion; version v1.<YYYYMMDDHHMM>;
retires other rows; single global production model; transaction.atomic; logs MODEL_TRAINED.

Serving (registry.py):
- get_production_bundle(): thread-safe (Lock) cached load; finds ModelVersion
  status=PRODUCTION newest; resolves path relative to BASE_DIR; raises ModelUnavailableError
  (503 MODEL_UNAVAILABLE) if none/missing/corrupt - "a prediction is never fabricated".
- predict(features_dict): validate all 8 present -> (1,8) array in FEATURES order ->
  Preprocessor.from_dict transform -> predict_proba -> argmax -> label; stashes
  _predicted_index/_predicted_label on bundle for SHAP; returns {risk_level,
  probabilities{cls:4dp}, probability, model{name,version,id}, explanation}.
- feature_importance(bundle): global feature_importances_ sorted desc.

13. Preprocessing
=====================================================================================
Only learned transform = median imputation (mlcore/preprocessing.py). Training: fit on
X_train -> np.nanmedian per column (NaN median -> 0) -> transform train/val/test.
Inference: medians ride inside the joblib bundle; predict() rebuilds via from_dict.
Training and inference share the same numbers by construction (parity, no train/serve skew).
Encoding: none (features numeric); label encoding = fixed RISK_LEVEL_ORDER index map.
Scaling: none (trees). Range checking: twice - data-cleaning drop + API serializer
validation, same constants file.

=====================================================================================
14. Risk Classification
=====================================================================================
Comes from the MODEL's argmax over 3 class probabilities:
  proba = model.predict_proba(X)[0]; predicted = classes[argmax(proba)].
risk_level = argmax class name; probability = its prob; probabilities = full dict.
No thresholds, no label-encoder file, no UI-only labels.
Rule engine runs in PARALLEL and does NOT override the ML class - it produces a separate
rules.category and (when != NORMAL) an Alert. Rules only "outrank" ML in the CHAT/UX
escalation path (LLM bypassed on emergency).
Three levels = dataset canonical labels (constants: "Do not invent others"); mirrored in
Prediction.risk_level choices, UI badges, chart colors.

=====================================================================================
15. SHAP Explainability
=====================================================================================
- What/why: SHAP attributes each feature's contribution to a prediction; here it lets a
  worker see why the model said "high risk". explain.py wording rule: SHAP values describe
  contributions to the MODEL'S PREDICTION, never medical causation about the patient.
- Where: mlcore/explain.py explain_prediction(bundle, vector), called from
  registry.predict() after probability computation, on the same preprocessed vector.
- How: shap.TreeExplainer(model).shap_values(vector); compatibility ladder for
  sklearn/xgboost output shapes (3-D -> slice predicted class; 2-D; legacy list).
  Takes top 8 by absolute impact; each item {feature, label (FEATURE_LABELS), value,
  impact (4dp), direction increasing/decreasing/neutral}. Response includes method
  "SHAP (TreeExplainer)", target_class, and anti-causation disclaimer.
- Failure: wrapped in try/except - "Explainability must never take the prediction endpoint
  down" - falls back to {method:"unavailable", features:[]}; prediction still returned.
- Persistence: stored on Prediction.explanation JSON; re-shown without recomputation.
- Frontend: charts/index.jsx ShapBars - horizontal Recharts bars, red (#c0392b) = positive
  impact (pushed risk up), green (#2e7d5b) = negative, zero reference line; rendered in
  PredictionResult and Overview tab, always with Disclaimer.
- Positive/negative meaning: positive = increased predicted-class probability (red),
  negative = decreased it (green). Statistical contributions, not causes.

16. Rule-Based Safety Engine
=====================================================================================
Files: assessments/rules/rules.json (data), engine.py (evaluator), keywords.py (chat
text -> symptom tokens), __init__.py (exports evaluate, load_rules).
Categories (ranked CATEGORY_RANK): NORMAL(0) ATTENTION(1) HIGH_CONCERN(2) EMERGENCY(3).

The 21 rules (v1), verbatim thresholds:
- EMERGENCY: EMER-CONVULSIONS, EMER-BLEEDING, EMER-BREATHING (symptom); EMER-BP-HIGH
  sys>=160; EMER-BP-DIA dia>=110; EMER-TEMP temp>=104F; EMER-HR-HIGH HR>=140.
- HIGH_CONCERN: symptoms severe_headache, blurred_vision, severe_abdominal_pain,
  decreased_fetal_movement, swelling_face_hands; HC-BP-SYS>=140, HC-BP-DIA>=90,
  HC-HR-HIGH>=120, HC-FEVER>=100.4F.
- ATTENTION: symptoms persistent_vomiting, dizziness_fainting, fever; ATT-HR-LOW HR<55;
  ATT-BMI-LOW BMI<18.5; ATT-BMI-HIGH BMI>=30.
rules.json governance note: thresholds are configurable defaults aligned with clinical
guidance ranges and "MUST be reviewed and approved by qualified clinical stakeholders."

Mechanics (engine.py):
- load_rules() caches JSON keyed by file mtime (hot-reload).
- _matches: symptom = token membership; vital = operator table {>=,>,<=,<,==}.
- evaluate(vitals, symptoms): collect all triggered; worst = highest-rank category;
  escalate = worst in (EMERGENCY, HIGH_CONCERN); returns category, escalate, rules_version,
  human message, ordered trigger list {id, category, description}.
Design: explicit (every rule a JSON row), versioned (stamped on every outcome), testable
(pure function), explainable (ids + descriptions).

Precedence with ML: assessments -> ML and rules are independent outputs (both persisted;
Alert when != NORMAL). Chat -> rules checked FIRST; if escalate, LLM bypassed entirely
(generation_mode=escalation) + RULE_ESCALATION audit. Engine docstring: "Emergency rules
outrank the ML model, RAG and the LLM. Nothing downstream may soften or hide an emergency."

Why separate from ML: statistical models can miss deterministic danger thresholds; a rule
set is inspectable, auditable, versioned, guaranteed to fire.

19. Risk Trend
=====================================================================================
Algorithm (assessments/trends.compute_trend, input = oldest-first series):
1. Empty -> {status:"no_data", direction:"unknown"}.
2. current = last risk_level; previous = second-to-last if >=2.
3. One visit -> status:"baseline".
4. Else diff = RISK_LEVEL_ORDER[current] - RISK_LEVEL_ORDER[previous] (low=0,mid=1,high=2):
   - increasing (diff>0) -> status "increasing"; decreasing (diff<0) -> "improving";
     stable (diff==0) -> "stable". "improving means a move to a lower-risk class."
5. Returns also sequence (all levels) and visits count.

Historical trend != future prediction - enforced:
- trends.py docstring: "descriptive analytics over stored predictions... does NOT predict
  future risk (no temporal model is trained; the dataset has no visit-level fields)."
- RiskTrendView response ships "Trends describe stored assessments only. The system does
  not predict future risk."; tests assert it.
- UI repeats it under every chart; PDF too.
- Only temporal ML code is quarantined research module mlcore/synthetic.py (Cholesky,
  flagged is_synthetic, quality-gated, never in production training).

21. AI Assistant
=====================================================================================
Pipeline (chat/services.respond):
1. User ChatMessage persisted immediately.
2. detect_symptoms(text) (rules/keywords.py): lexical phrase matching - e.g.,
   "convulsion/seizure/fit/eclampsia" -> convulsions; "baby not moving" ->
   decreased_fetal_movement. No LLM.
3. Rules FIRST: if symptoms detected, latest assessment's vitals loaded and
   rules_evaluate(vitals, detected) runs. Design comment: only high-concern/emergency
   WORDS IN THE MESSAGE ITSELF escalate - stored vitals alone never hijack a chat about
   nutrition (vitals only injected when symptoms detected).
4. Escalation branch: deterministic answer from rules_out message + triggered ids + "This
   chat assistant cannot provide emergency care."; saved with generation_mode="escalation";
   audited RULE_ESCALATION; returned without RAG or LLM.
5. Normal branch: _patient_context() = latest prediction only -> one line ("latest assessed
   risk category... model confidence ...%") + gestational week. Minimal, authorized, no
   sensitive history.
6. rag.retrieve_context(question) -> top chunks.
7. History: last 12 messages (final user turn dropped, passed as question explicitly).
8. llm.generate_answer(question, context_chunks, history, patient_context) -> (answer, mode).
9. Fallbacks: LLM unconfigured/fails/empty -> if chunks: FALLBACK_NO_LLM + verbatim excerpts
   ([title - chunk n]) mode="rag_only_fallback"; else FALLBACK_NO_LLM + "No indexed knowledge
   matched..." mode="no_llm_configured".
10. Assistant message persisted with sources (title, url, chunk_index, score), escalation
    summary, generation_mode; audited CHAT_ACCESS; serialized with CHAT_DISCLAIMER.

Storage: ChatSession per patient (title auto-set from first message first 60 chars);
ChatMessage per turn.

LLM call (chat/llm.py): OpenAI-compatible client (api_key, base_url, timeout 45s),
model settings.LLM_MODEL (default gpt-4o-mini), temperature=0.3, max_tokens=600.
System prompt forbids diagnosing/prescribing/certainty/exam claims; demands grounding in
excerpts; cautious language; <250 words. generate_answer raises nothing - any exception
logged, fallback returned.

The assistant does NOT diagnose - prompt, disclaimers, and chat UI all enforce it.

22. RAG / Knowledge Base
=====================================================================================
- Ingestion: kb/views.py KnowledgeDocumentListCreateView.perform_create - admin uploads
  PDF/TXT/MD or pastes text; sha256 stored; indexing ValueError -> document deleted + 400.
- Extraction: kb/services/ingestion.extract_text - .pdf via pypdf (PdfReader page join),
  .txt/.md read UTF-8, else content_text.
- Chunking: ingestion.chunk_text - 900-char chunks, 150-char overlap (CHUNK_SIZE,
  CHUNK_OVERLAP); empty text -> [].
- Embedding: embeddings.py - local TF-IDF (TfidfVectorizer max_features=5000,
  stop_words=english) fitted over whole corpus at index time (fit_corpus from indexing;
  other docs re-embedded via _reembed_others); openai text-embedding-3-small.
- Indexing: indexing.index_document - @transaction.atomic; deletes old chunks, embeds,
  bulk_create DocumentChunk rows (vector lists + backend tag); sets chunk_count, indexed_at.
- Storage: DocumentChunk.embedding JSONField = the vector store in default backend.
- Retrieval: store.retrieve (load all vectors, L2-normalize, cosine = matrix @ query.T,
  top-k) + rag.retrieve_context (MIN_SCORE=0.05 filter; returns {document_id,
  document_title, source_url, chunk_index, text<=1200, score}; never raises - empty/failed
  KB -> None).
- Citation: chat/services -> ChatMessage.sources -> ChatPanel collapsible "Knowledge-base
  sources (n)". Every non-escalation answer carries sources.
- APIs: GET/POST /api/rag/documents/, GET/PATCH/DELETE .../<pk>/, GET .../chunks/,
  POST /api/rag/reindex/ (admin), POST /api/rag/retrieve/ (probe).

36. Security Analysis
=====================================================================================
Implemented (verified in code):
- Password hashing via Django set_password everywhere; passwords never serialized.
- AUTH_PASSWORD_VALIDATORS + validate_password on change/create.
- JWT: short access (30m), blacklistable refresh, role+active revalidation on refresh,
  generic 401 messages.
- Role permissions + object-level patient scoping reused everywhere; explicit patient
  parameter required (no accidental cross-record access).
- Structured errors never leak stack traces (debug_trace DEBUG-only).
- Audit logging with REDACTED_KEYS (password, token, access, refresh, secret, ssn) +
  "never store medical values or chat content"; admin-only read.
- ORM-only queries -> SQL injection structurally prevented; no raw SQL.
- XSS: React escapes; no dangerouslySetInnerHTML anywhere.
- File-download authorization (ReportDownloadView, tested).
- Input validation at 3 layers (UI, serializer, rule plausibility); chat length cap.
- Generic password-reset response (no enumeration). Soft-delete users. .gitignore excludes
  .env/db/media/artifacts.

Should be improved (gaps, honestly stated):
1. Committed-looking API key in .env.example - rotate/revoke/purge. TOP PRIORITY.
2. Tokens in localStorage (XSS-exfiltratable); httpOnly cookies safer.
3. No rate limiting/throttling on login or chat (DRF throttles not configured).
4. django admin relies on session/CSRF - fine but dual auth scheme.
5. pages/hcw/Reports.jsx direct /media/ link bypasses authorized download.
6. pypdf / dj_database_url missing from requirements.
7. Password-reset flow incomplete on frontend: no /reset-password route.
8. JWT stateless - stolen access token valid up to 30 min; no token binding.
9. No explicit SECURE_* settings (HSTS, secure cookies, SSL redirect).
10. audit ip_address trusts X_FORWARDED_FOR first (spoofable unless proxy strips it).
11. Model artifact integrity not verified at load.

37. Error Handling
=====================================================================================
Backend layers:
- core/exceptions.py contract: every DRF error -> {success:false,error{code,message,details}}.
  Http404->NOT_FOUND; PermissionDenied->PERMISSION_DENIED; ApiError -> its code/status;
  ValidationError -> VALIDATION_ERROR + field details; NotAuthenticated/AuthenticationFailed
  -> AUTHENTICATION_ERROR; set_rollback on API exceptions; unhandled -> logged + opaque
  INTERNAL_ERROR 500. flatten_error_messages makes field errors a readable sentence.
- core/middleware.py: StructuredErrorMiddleware converts HTML 404/500 on /api/* to JSON;
  process_exception returns 500 JSON (debug_trace only in DEBUG).
- Domain fail-safes: ModelUnavailableError->503 with hint (never fabricate); SHAP failure ->
  method "unavailable" (never takes endpoint down); llm.generate_answer raises nothing;
  rag.retrieve_context never raises -> None; chat fallback modes; create_assessment
  transaction.atomic (all-or-nothing); log_event never breaks request; KB ValueError ->
  delete + 400; activate 404 ApiError; send message 400 on empty/long.

Frontend layers:
- api/client.js: single-flight 401 refresh-and-retry; on failure clear tokens + broadcast
  aimhra:logout (guards redirect to /login). apiError normalizes envelopes + network errors.
- Component pattern: Loading -> ErrorState(retry) -> EmptyState -> content; forms map
  error.details onto field errors; ChatPanel inserts "Sorry - <msg>" assistant bubble.

Failure traces:
Invalid login -> 401 AUTHENTICATION_ERROR + LOGIN_FAILED audit -> red alert.
Invalid assessment -> 400 VALIDATION_ERROR field details -> inline errors; nothing saved.
No model -> 503 MODEL_UNAVAILABLE -> aborts before ANY write.
Corrupt artifact -> 503 with artifact-path message.
SHAP crash -> prediction returned, explanation method="unavailable".
LLM down/unset -> rag_only_fallback or no_llm_configured (visible modes).
Report by stranger -> 403 (tested).
Any unhandled error -> 500 JSON, stack only in logs (trace only in DEBUG).

selection; local vector store default; LLM output not programmatically verified against
sources (prompt-enforced grounding); no push notifications (alerts are pull-based).

42. How to Explain This Project in a Viva (short answers)
=====================================================================================
What is the project? A role-based maternal-health decision-support system. Healthcare
workers record patient visits; an ML model classifies risk (low/mid/high) with
probabilities; SHAP explains it; an independent rule engine raises safety alerts; history,
trends, PDF reports, and a RAG-grounded assistant complete the workflow. Two staff roles.
Why Django? ORM, auth (extensible User), migrations, admin, DRF - the safety layer plugs in
as ordinary apps inside the same transactional boundary.
Why React? Highly interactive staff console - tabbed workspaces, live forms, charts;
component model + router + recharts.
Why REST API? Forces safety-critical logic server-side where it can't be bypassed; thin SPA;
uniform envelope lets one axios client handle auth/refresh/errors.
Why JWT? Stateless API auth; 30m access + 7d refresh blacklisted at logout; refresh
re-validates role + is_active from DB.
Why XGBoost and Random Forest? Strong tabular classifiers, no scaling, predict_proba +
feature_importances_; train both on identical splits; selection by high-risk-recall-first
(because a missed high-risk case is the costliest error). Accuracy never sole basis.
Why SHAP? Tree ensembles are black boxes; TreeExplainer gives per-feature contributions for
the predicted class, persisted for reproducibility; red = pushes risk up, green = down;
labeled as statistical, not causal.
Why rule-based alerts in addition to ML? Model is probabilistic; emergencies must be
deterministic (systolic >= 160 always escalates even if model says low risk). Versioned JSON
rules are inspectable by clinicians.
Why three risk levels? The dataset target has exactly three classes; inventing others would
break train/serve consistency.
Why a database? Longitudinal clinical value: each visit's inputs + exact model output stored
(with model_ref) -> history, trends, reports, alerts, audit, reproducibility.
Why RAG? So the assistant answers from trusted, cited documents, not LLM memory; top-5 above
min score; prompt-constrained grounding; sources stored + rendered.
Why a vector store/embeddings? Match question to document passages by meaning; chunks
embedded (TF-IDF default, OpenAI optional) and ranked by cosine; local backend = zero infra,
Qdrant swap-in.
Why an AI assistant? Education/navigation; emergency rule engine checked FIRST and bypasses
the LLM, so it can never talk a user out of seeking care.
Why PDF reports? Assessments must be shareable/archival; ReportLab backend = one source of
truth; download re-checks authorization per request.
Why role-based access? Least privilege; worker sees only created/assigned patients
(can_access_patient); admin manages users/models/KB/audit; same selector backs every endpoint.
What's innovative? The combination: explainable ML persisted per prediction, a deterministic
rule engine that provably outranks model + LLM, honest descriptive-only trends, versioned
model governance, audit with redaction, graceful degradation (503 instead of fabrication,
excerpt-fallback chat).
Limitations? Single dataset, glucose unit inconsistency, no rate limiting, JWT in
localStorage, local vector store loads everything, trends only last two visits, no FE tests,
no deployment config.
Future work? Rotate/purge exposed key; httpOnly-cookie auth; throttling; temporal dataset for
real longitudinal modeling; Qdrant scale; background re-indexing; FE tests; Dockerized
deploy with Postgres; clinical sign-off of rules.

43. Viva / Defense Question Bank (with answers grounded in this repo)
=====================================================================================
PROJECT OVERVIEW
1. What does AIMHRA stand for? "Hybrid AI-Based Maternal Health Risk Analysis and
   Healthcare Decision-Support System" (config/settings.py).
2. Who are the users? HEALTHCARE_WORKER and ADMIN only; patients never log in.
3. What happens on an emergency finding? Rule engine EMERGENCY -> Alert row + RULE_ESCALATION
   audit + red banner; in chat the LLM is bypassed entirely.
4. How many rules? 21 in rules.json v1 across four categories; each has id, category,
   type (symptom/vital), description.

ARCHITECTURE
5. Walk a request through the system. Vite proxy -> Django URL -> DRF JWT auth ->
   permission -> view -> serializer -> service -> ORM -> engine (ML/rules) -> envelope ->
   axios unwrap -> React state.
6. Where is business logic? Services/selectors (assessments/services.py, patients/selectors.py,
   reports/services.py, chat/services.py, kb/services/*), not views.
7. What is core/ for? Cross-cutting infrastructure: permissions, error contract, error
   middleware, pagination, success helper.

DJANGO / DRF
8. Why a custom exception handler? Guarantee one error shape + code mapping +
   flatten_error_messages for readable field errors + set_rollback for data safety.
9. How does pagination work? StandardPagination (20/page, page_size param, max 100).
10. What does drf-spectacular provide? Auto OpenAPI schema + Swagger UI.

REACT
11. How does the app restore a session on reload? AuthContext sees stored access token ->
    GET /api/auth/profile/; failure clears tokens.
12. What happens on a mid-session 401? Response interceptor refreshes once (single-flight),
    retries; on failure clears tokens + broadcasts aimhra:logout; context clears user.
13. How is route protection done? ProtectedRoute checks boot state, user existence, two valid
    roles, then optional roles array; wrong role -> own dashboard.

DATABASE
14. Why is Prediction separate from Assessment? One visit, one derived output pinned to
    model_ref; keeps raw inputs immutable, model outputs versioned.
15. Why SET_NULL on many FKs? Preserve clinical history if the acting user/model row is removed.
16. What do migrations 0002 do? Role refactor: PATIENT removed, legacy accounts deactivated
    (accounts/0002); patient identity copied onto record + user FK dropped (patients/0002).

AUTHENTICATION
17. Where is the login role check? CustomTokenObtainPairSerializer.validate rejects roles
    outside HCW/ADMIN; repeated at refresh.
18. How is logout real if JWT is stateless? Refresh token blacklisted; access expires in 30m.

ML
19. Describe the split and why. Stratified 70/15/15, random_state=42; metrics from test only.
20. What preprocessing? Median imputation fitted on training split only, persisted in bundle;
    no scaling (trees).
21. What if age=300 posted? Serializer range check -> 400; same ranges removed training rows.
22. How is production chosen? selection_score with high_risk_recall_then_f1 criterion;
    train_models retires others, marks winner PRODUCTION.
23. What if no model registered? ModelUnavailableError -> 503; assessment not saved (tested).
XGBOOST / RF SPECIFICS
24. Key hyperparameters? RF: 400 trees, min_samples_leaf=2, class_weight=balanced_subsample.
    XGB: 400 rounds, lr 0.08, depth 6, subsample 0.9, colsample 0.8, hist, mlogloss.
25. Why class weights if balanced? Near-balanced so resampling rejected; weights kept as
    safeguard; recorded in TRAIN_CONFIG.

SHAP
26. Which model, when? Production bundle, right after predict_proba, same vector; top-8.
27. What do positive SHAP values mean? Feature pushed predicted-class probability up (red);
    negative down (green) - model-level, not causal.

RULES / ALERTS
28. Can ML hide an emergency? No - rules run independently; EMERGENCY creates its own Alert
    and, in chat, bypasses LLM.
29. How to add a rule? Add a row to rules.json; engine hot-reloads on mtime; bump version.
30. Alert lifecycle? OPEN -> ACKNOWLEDGED -> RESOLVED via /ack/, recording acknowledged_by.

RAG / LLM / VECTOR
31. Chunking? 900 chars with 150 overlap; empty -> no chunks -> clean 400.
32. How is hallucination mitigated? Grounding prompt, cautious language, <=250 words, stored
    + displayed sources, excerpt fallbacks.
33. Default embedding/vector store? Local TF-IDF + numpy cosine over JSON vectors; Qdrant
    optional, not installed.
34. Empty KB? retrieve_context -> None; chat says no indexed knowledge matched - no fabrications.
35. Which LLM? Any OpenAI-compatible; default gpt-4o-mini, temp 0.3, max 600 tokens, 45s timeout.

SECURITY
36. Where could SQL injection occur? Nowhere - all queries ORM; no raw SQL.
37. How are downloads protected? /api/reports/<id>/download/ re-checks can_access_patient;
    stranger 403 tested.
38. Weakest security point? Exposed-looking key in .env.example; tokens in localStorage;
    no login throttling.

TESTING / DEPLOYMENT
39. How do tests get a model without long training? train_all(quick=True) -> 10-tree models.
40. How would you deploy? Postgres via DATABASE_URL, gunicorn behind nginx, DEBUG=False, real
    SECRET_KEY, collectstatic, media on CDN/object storage, HTTPS - none configured in repo,
    and I'd say so clearly.

44. Final Complete System Summary
=====================================================================================
AIMHRA is a staff-facing maternal-risk decision-support platform whose defining quality is
defensive engineering: every stage of the pipeline has an explicit failure mode, an explicit
disclaimer, and an explicit audit trail.
- Identity & access: custom User with two roles; JWT access (30m) + blacklisted refresh
  (7d); role re-validated at login AND refresh; object-level patient access via one shared
  selector; legacy PATIENT role removed by migration and blocked at three layers.
- Clinical workflow: standalone patient records (created-or-assigned visibility) -> visit
  assessments capturing exactly 8 model features + fixed symptom vocabulary -> serializer
  validation mirroring training-data plausibility ranges -> atomic persistence of
  Assessment + Prediction + Alert.
- Intelligence: RF and XGBoost trained on a documented, cleaned 6,057-row dataset (stratified
  70/15/15, median-imputation preprocessor persisted in the artifact); production selection
  by high-risk-recall-first criterion; versioned ModelVersion registry; every prediction
  stamped with exact model name/version and a persisted SHAP top-8 explanation with an
  anti-causation disclaimer.
- Safety: a deterministic, versioned 21-rule engine (NORMAL->ATTENTION->HIGH_CONCERN->
  EMERGENCY) that outranks the model, RAG, and LLM; alerts with a full acknowledge/resolve
  lifecycle; chat messages scanned lexically for emergency phrases with LLM-bypassing
  escalation.
- Longitudinal view: history and trend computed ONLY over stored predictions (last-two-visit
  comparison -> improving/stable/increasing), explicitly and repeatedly labeled as
  non-predictive.
- Knowledge & assistance: admin-curated RAG pipeline (PDF/TXT ingestion -> 900/150 chunking
  -> TF-IDF or OpenAI embeddings -> cosine top-5 retrieval with score floor -> cited,
  prompt-constrained OpenAI-compatible generation with excerpt fallbacks).
- Output & oversight: ReportLab PDFs generated and authorization-checked server-side; an
  admin console for users, assignments, model comparison/activation, knowledge management,
  and system stats; an admin-only audit log of 19 action types with key redaction.
- Quality posture: layered tests across auth, scoping, ML serving, rules, trends, RAG, chat
  safety, and reports, plus a runnable end-to-end smoke script; structured error envelope
  end-to-end; graceful degradation at every external dependency (model, SHAP, LLM, KB).

KNOWN DEBTS, RANKED: the exposed-looking API key in .env.example (rotate/scrub immediately);
missing pypdf dependency; token storage and throttling; the unauthorized /media/ report
link; the incomplete password-reset landing route; first-page-only lists in the UI; the
shared-bundle mutation race in predict(); and the absent deployment configuration. None of
these undermine the architecture - all are addressable without structural change.

After reading this report, every layer of the repository - from rules.json thresholds to the
axios refresh interceptor, from the TF-IDF refit strategy to the RISK_LEVEL_ORDER trend
arithmetic - can be opened, located, explained, and defended.
